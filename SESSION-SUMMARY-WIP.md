## 5. Frontend Architecture (polaris-wms-fe/apps/remote-document)

### Vite Proxy Config (vite.config.ts)
```
/api/v1/templates/*           → rewrite to /document/api/v1/templates/*       @ localhost:8080
/api/v1/template-assignments/* → rewrite to /document/api/v1/template-assignments/* @ localhost:8080
/api/v1/documents/*           → rewrite to /document/api/v1/documents/*       @ localhost:8080
/api/v1/pdf/*                 → rewrite to /document/api/v1/pdf/*             @ localhost:8080
```

### Key Design Decisions
1. `@polaris/service` fetcher HARD-OVERRIDES `reqConfig.baseURL = '/api/v1'` on every request (fetcher.ts line ~131) — so relative paths rely on a proxy to add `/document` + host. **Document addressing is now PROXY-BASED (see section 14)** — the frontend emits ONLY relative paths, and a proxy/gateway inserts `/document`:
   - fetcher calls send paths relative to `/api/v1` (e.g. `/templates/getAll`, NOT `/api/v1/...`) — fetcher prepends `/api/v1`.
   - blob `fetch()` calls send the full `/api/v1/...` path via `blobUrl()` (native fetch gets no baseURL).
   - Dev: Vite proxy (shell + standalone) rewrites `/api/v1/...` → `/document/api/v1/...`. Prod: Nginx/ingress must do the same rewrite.
   - **The old `docUrl()` / `VITE_DOCUMENT_API_URL` absolute-URL approach (section 13) was REVERTED this session** — it caused `/api/v1/api/v1/...` path doubling in dev (see section 14).
2. `DEFAULT_HEADERS` in `template.api.ts` ensures `user-username` header is always sent (fallback: 'system')
3. `Template.templateContent` is a string (JSON elements array or raw HTML/ZPL) — NOT a structured object
4. `TemplateContext` separates `state.template` (metadata) from `state.elements` (parsed array from templateContent)
5. Elements parsed via `parseElements(templateContent)`, serialized via `serializeElements(elements)` on save
6. Blob responses (PDF generate, proxyPdf, cropPdf) use native `fetch()` — fetcher doesn't support responseType blob

### 12.4 CRITICAL: Shell → Backend Proxy (the connectivity fix)
When remote-document runs INSIDE the shell, its API calls (`/api/v1/templates/getAll`) go through the
SHELL's dev-server proxy (port 3000), NOT the remote's own proxy (which only applies on port 5010 standalone).
The shell previously had only a generic `/api` → master-data service rule, so document calls 500'd.

Added to `apps/shell/vite.config.ts` `server.proxy` (BEFORE the generic `/api`):
```ts
'/api/v1/templates': {
  target: env.VITE_DOCUMENT_API_URL || 'http://localhost:8080',
  changeOrigin: true,
  rewrite: (p) => p.replace(/^\/api\/v1\/templates/, '/document/api/v1/templates'),
},
'/api/v1/template-assignments': { /* same, rewrite → /document/api/v1/template-assignments */ },
'/api/v1/pdf': { /* same, rewrite → /document/api/v1/pdf */ },
// then the existing '/api' → VITE_API_BASE_URL (master-data), '/auth', '/sessions' rules
```
> Proxy order matters — Vite matches top-to-bottom, so document rules must precede the `/api` catch-all.
> This is DEV-ONLY. Production needs the API gateway/ingress to route `/document/...` to the document service.

## 13. Session — Deployed 500 Fix + Local remoteEntry Diagnosis (⚠️ 13.3 APPROACH REVERTED — see section 14)

> ⚠️ **The `docUrl()` / `VITE_DOCUMENT_API_URL` absolute-URL approach in 13.3–13.6 was REVERTED in the
> next session.** It was fundamentally flawed: in dev, `docUrl()` returned a relative `/api/v1/...`
> which the shared fetcher then re-prefixed with `baseURL='/api/v1'`, producing a DOUBLED path
> `/api/v1/api/v1/templates/getAll` → 404 (5010) / 500 (3000). See **section 14** for the current
> (proxy-based) design. Sections 13.1–13.2 (root-cause diagnosis) remain accurate and useful.

Two separate problems were diagnosed and (for the API one) fixed this session.

### 13.1 Local: "Failed to load remote module" (404/HTML on remoteEntry.js)
Same root cause as gotcha 12.5, re-confirmed live. Running the remote with `pnpm run dev` on :5010
serves the SPA `index.html` (Content-Type `text/html`, contains `/@react-refresh`) at
`/assets/remoteEntry.js` because `@originjs/vite-plugin-federation` only emits `remoteEntry.js` at
BUILD time, never in `vite dev`. The shell then fails to import it as a module.

**Fix (workflow, not code):** stop the `vite dev` process on 5010, then `pnpm run build` +
`pnpm run preview` on 5010. Verified: `GET http://localhost:5010/assets/remoteEntry.js` →
200 with `Content-Type: text/javascript` and real federation JS (exposes `./views/templates`).

> To find/kill the dev server on 5010: `netstat -ano | Select-String ":5010"` → note the PID on the
> LISTENING line → `Stop-Process -Id <pid> -Force`.

### 13.2 Deployed: API `getAll` returns 500
**Symptom:** deployed browser `POST http://10.193.1.228:30080/api/v1/templates/getAll` → 500.
Bruno (working) uses `baseUrl = http://10.193.1.228:30090/document` → `POST {{baseUrl}}/api/v1/templates/getAll`
= `.../document/api/v1/templates/getAll` → 200 OK.

**Root cause:** The document backend serves everything under its `/document` context path
(`APP_REST_SERVER.contextPath="/document"` in `.env` / `system.properties`, applied by helper-go's
`hrest` server — NOT in a route file). The frontend fetcher always emits a relative `/api/v1/...`
(no `/document`) and relies on a proxy to add the prefix + correct host/port. In DEV the Vite proxy
does this. In PROD there is no such proxy, so the call landed on the wrong origin/path (`:30080`,
no `/document`) and 500'd. (Note prod document service is on `:30090/document`, not `:30080`.)

**Backend needs NO change** — it correctly owns `/document/api/v1/...` only.

### 13.3 Fix applied (frontend, document-scoped, shared fetcher untouched)
Added a document-specific base URL in `apps/remote-document/src/api/template.api.ts`:
```ts
const DOCUMENT_API_HOST = (import.meta.env?.VITE_DOCUMENT_API_URL as string | undefined)?.replace(/\/$/, '') || ''
const documentApiBase = () => DOCUMENT_API_HOST ? `${DOCUMENT_API_HOST}/document/api/v1` : '/api/v1'
const docUrl = (path: string) => `${documentApiBase()}${path}`
```
- **Dev** (`VITE_DOCUMENT_API_URL` empty): `docUrl('/templates/getAll')` → `/api/v1/templates/getAll`
  (relative) → existing Vite proxy rewrites to `/document/...`. Unchanged behavior.
- **Prod** (`VITE_DOCUMENT_API_URL=http://10.193.1.228:30090`): →
  `http://10.193.1.228:30090/document/api/v1/templates/getAll` (ABSOLUTE). Axios ignores its own
  `baseURL` for absolute URLs, so this bypasses the shared fetcher's `/api/v1` override WITHOUT
  editing `fetcher.ts` or `config.ts`.

All document calls were routed through `docUrl()`:
- 7 fetcher calls: templates getAll/detailById/save/edit/delete, template-assignments assign/getByScope/getByTemplateId
- 4 blob `fetch()` calls: templates/generate, documents/preview, pdf/proxyPdf, pdf/cropPdf
